# بستهٔ گردشکار (Workflow package) — راهنمای داخلی ما

این راهنما برای خودمان است، نه برای مشتری. مشتری فقط فایل امضاشده را می‌گیرد.

## ساده‌ترین راه: «ساز گردشکار» (بدون نوشتن JSON)
1. فایل `Workflow-Studio.cmd` (در پوشهٔ اصلی پروژه) را دابل‌کلیک کنید؛ صفحهٔ «ساز گردشکار هورمند» در مرورگر باز می‌شود (فقط روی همین رایانه).
2. با فرم بسازید: نام، چه کسانی شروع کنند، فیلدهای فرم، و مرحله‌ها (تأیید، کار، شرط، اطلاع‌رسانی، پایان) با انتخاب‌گر. بالا دو نمونه هست که می‌شود از آن‌ها شروع کرد.
3. هر لحظه سمت چپ می‌نویسد فایل درست است یا چه چیزی کم دارد، و پیش‌نمایش مراحل را نشان می‌دهد.
4. «ساخت و امضا» را بزنید: فایل امضاشده در `Documents\Hoormand-Workflows` ساخته می‌شود (همان فایلی که به مشتری می‌دهید).
5. «بارگذاری و روشن کردن در دموی لوکال» را بزنید تا همان لحظه در دمو (`localhost:8095`) بارگذاری و روشن شود؛ بعد با یک کاربر عادی (مثلاً `peyman@demo.local` / `demo`) در «امور اداری ← گردشکارها» امتحانش کنید.
6. «ذخیرهٔ پیش‌نویس» و «باز کردن یکی از ذخیره‌شده‌ها» برای ادامهٔ کار بعداً (برای تغییر، نسخه را بزرگ‌تر کنید).

(همین کار با دستور: `cd server` و `go run ./cmd/wfpack studio`؛ پورت یا پوشه با `-port` و `-dir`.)

## ایده
مشتری یک مسیر کار خاص دارد (مثلاً «تأیید خرید با شرط مبلغ»). ما آن را در یک فایل JSON می‌نویسیم، با کلید خودمان **امضا** می‌کنیم و می‌دهیم. مدیر سیستم مشتری فایل را در «پنل مدیریت ← تنظیمات سیستم ← گردشکارها» بارگذاری و **روشن** می‌کند. گردشکار کنار گردشکارهای آمادهٔ سامانه (مرخصی، نامه، پیش‌فاکتور…) در «امور اداری ← گردشکارها» می‌آید و آن‌ها را عوض نمی‌کند. با خاموش یا حذف کردن فایل، سامانه دقیقاً مثل قبل می‌شود.

مشتری **نمی‌تواند** چیزی در فایل عوض کند: امضا روی کل متن فایل است و با کوچک‌ترین تغییر سرور فایل را رد می‌کند («فایل بعد از امضا تغییر کرده است»). هر تغییر یعنی نسخهٔ تازه از طرف ما.

## ساخت یک بسته برای مشتری
1. فایل `نام.json` را با قالب پایین بنویسید (نمونه‌ها در `server/internal/workflow/examples/`).
2. بررسی کامل (مرحله‌ها، افراد، مقصدها، دست‌نخورده نماندن مرحله):
   `go run ./cmd/wfpack check نام.json`
3. امضا:
   `go run ./cmd/wfpack sign نام.json` ← فایل `نام.signed.json` ساخته می‌شود؛ این فایل را به مشتری بدهید.
4. (اختیاری) بررسی امضا: `go run ./cmd/wfpack verify نام.signed.json`

دستورها را از پوشهٔ `server` اجرا کنید.

## کلید امضا
- فایل کلید خصوصی: `C:\Users\<شما>\.hoormand\workflow-signing.key` (روی همین رایانه، **بیرون از پروژه**). هرگز کامیت نشود و به مشتری داده نشود.
- **از آن یک نسخهٔ پشتیبان بگیرید.** اگر گم شود، دیگر نمی‌شود بستهٔ تازه امضا کرد.
- کلید عمومی در `server/internal/workflow/keys.go` است (شناسهٔ `hoormand-1`). برای عوض کردن کلید: `wfpack keygen -key <فایل تازه>`، یک شناسهٔ جدید به `keys.go` اضافه کنید (کلید قدیمی را تا وقتی فایل‌های قدیمی هست نگه دارید) و در `cmd/wfpack/main.go` شناسه را عوض کنید.

## قالب فایل (`format: hoormand-workflow/1`)
```json
{
  "format": "hoormand-workflow/1",
  "id": "purchase-approval",        // انگلیسی کوچک، عدد و خط تیره
  "version": 1,                     // هر تغییر = نسخهٔ بزرگ‌تر
  "name": "درخواست خرید تجهیزات",
  "description": "توضیح کوتاه که کاربر در کارت می‌بیند",
  "customer": "نام مشتری (فقط برای خودمان)",
  "start": { "allow": [{ "kind": "everyone" }], "title": "خرید {{item}}" },
  "fields": [ { "key": "item", "label": "کالا", "type": "text", "required": true } ],
  "steps": [ ... ]
}
```
**نوع فیلد:** `text` `textarea` `number` `money` `date` `select` (با `options`) `person` (انتخاب همکار) `yesno`.
**عنوان:** `{{کلید فیلد}}` با مقدار فرم پر می‌شود.

### افراد (`who` / `to` / `allow` / `escalate`)
| kind | یعنی |
|---|---|
| `everyone` | همهٔ همکاران (فقط در `start.allow`) |
| `starter` | درخواست‌دهنده |
| `starterManager` | مدیر واحدِ درخواست‌دهنده (اگر نداشت: مدیرعامل) |
| `ceo` | مدیرعامل (کسی که «امضای نامهٔ رسمی» دارد) |
| `admin` | مدیران سیستم |
| `user` + `ref` | یک نفر؛ ref = ایمیل، شناسه یا نام کامل |
| `unit` + `ref` | مدیر واحد با آن نام |
| `unitMembers` + `ref` | همهٔ افراد آن واحد |
| `field` + `ref` | فردی که در فیلد `person` با آن کلید انتخاب شده |

### مرحله‌ها (ترتیب آرایه = ترتیب خواندن؛ مرحلهٔ اول شروع است)
- **`approval`**: `who`، `mode` (`any` پیش‌فرض یا `all`)، `hours` (مهلت)، `escalate` (بعد از مهلت اینها هم خبر می‌گیرند و می‌توانند تصمیم بگیرند؛ با `all` ممکن نیست)، `next`، `onReject` (اگر ننویسید رد = پایان با «رد شد»). رد کردن دلیل لازم دارد. کسی درخواست خودش را تأیید نمی‌کند (به مدیرعامل می‌رود).
- **`task`**: مثل تأیید ولی با «انجام شد»؛ `who`، `hours`، `next`.
- **`condition`**: `if` = `{field, op, value}` یا `{all:[…]}` / `{any:[…]}`؛ `then` و `else` مقصد. عملگرها: `== != > >= < <= contains empty notEmpty`.
- **`notify`**: `to`، `text` (با `{{…}}`)، `next`.
- **`end`**: `outcome` = `approved` | `rejected` | `done`.

بررسی خودکار فایل: شناسهٔ تکراری، مقصد ناموجود، مرحلهٔ بدون راه از اول، نبودن پایان، فیلد ناموجود در شرط، نوع ناشناخته؛ کلید اضافه هم رد می‌شود.

## رفتار سامانه
- بارگذاری: فقط مدیر سیستم؛ فایل باید امضای ما را داشته باشد؛ نسخهٔ تکراری رد می‌شود. بعد از بارگذاری **خاموش** است.
- روشن کردن یک نسخه، نسخه‌های دیگر همان گردشکار را خاموش می‌کند.
- خاموش کردن فقط جلوی درخواست **تازه** را می‌گیرد؛ درخواست‌های در جریان تمام می‌شوند. حذف فقط وقتی ممکن است که درخواست در جریان نباشد.
- اگر مرحله‌ای هیچ‌کس پیدا نکند (نام اشتباه یا واحد بی‌مدیر)، درخواست **ثبت نمی‌شود** و دلیل را می‌گوید.
- هر مرحله اعلان می‌دهد (برچسب «گردشکار»)؛ مهلت گذشته هر ۱۰ دقیقه بررسی و یک بار اعلام می‌شود.
- مدیر سیستم می‌تواند به جای تأییدکننده تصمیم بگیرد (در تاریخچه «از طرف مدیر سیستم» ثبت می‌شود).
- تاریخچهٔ کامل هر درخواست (چه کسی، چه کاری، چه وقت، چه توضیحی) نگه داشته می‌شود.

## آزمون
- `go test ./internal/workflow/` : موتور، اعتبارسنجی و امضا (تغییر فایل، فایل بی‌امضا، امضای کلید دیگر).
- نمونه‌ها در دموی محلی روشن‌اند (نمونه‌های امضاشده در `internal/workflow/examples/*.signed.json` و در `demo.go` بارگذاری می‌شوند).

## هنوز نیست (مرحلهٔ بعد)
شرط‌های پیچیده‌تر روی چند مرحله، فرم هر مرحله، پیوست فایل، گزارش گلوگاه و ابزار تصویری ساخت. این‌ها بعد از دیدن اولین مشتری واقعی ساخته می‌شوند.
